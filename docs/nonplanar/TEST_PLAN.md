# План проверок

## Статусы и трассировка

`acceptance_tests.csv` — будущие системные тесты. Все строки поставлены в `NOT_IMPLEMENTED_NOT_RUN`. `requirements.json` покрывает 36 групп ТЗ; `backlog.json` связывает задачи/зависимости и tests. Наличие строки с expected=ACCEPT не означает, что реализация уже работает.

Различать три уровня: (1) проверки целостности этого комплекта; (2) автоматические тесты будущей Orca-модификации; (3) физические испытания принтера. Отчёты не смешивать.

## Аналитические fixtures

Генератор `scripts/generate_fixtures.py` создаёт замкнутые бинарные STL для блока, клиньев, цилиндрической крыши, пологого сферического сегмента, высокого купола, седла, волны и пары выступов. В `fixtures/catalog.json` — точные параметры и формулы. Генератор не создаёт G-code и не проверяет пригодность к печати.

Все модели — геометрические входы. Положительный oracle должен дополнительно задавать совместимый head/scene/material profile, mask целевой непланарной области, ожидаемые bounds, погрешность и допустимый процент обработки. «Любой профиль + сферический STL = ACCEPT» не является тестом.

Для плоскости использовать точный объём и градиент; для сферы — аналитическое расстояние/производные; для sweep через стену — точно известный пересекающийся интервал. Нужны отдельные fixtures с отверстиями, узкой впадиной, внутренними оболочками, дефектами STL и STEP-единицами; их реализация включена в backlog, они не объявляются уже созданными STL этого пакета.

## Измеримые положительные критерии

До первого запуска реализации зафиксировать ROI для положительных тестов. Например, в центральной области пологой крыши после исключения transition strip требуется не менее 90% заранее допустимой площади в непланарных дорожках и ненулевая амплитуда Z. Точный ROI зависит от tool fixture и фиксируется в test data, не выводится постфактум из областей, которые удалось обработать.

Для плоского блока допустима полностью планарная печать. Для высокого купола положителен ограниченный top patch и сохранение крутых боков. Если цель невозможна для выбранного инструмента, fixture исправляется независимым геометрическим обоснованием, а не ослаблением expected до «любой результат».

## Mutation и negative tests

Взять известное корректное задание, изменить ровно один фактор: координату среднего сегмента, E, F, nozzle flange, mode, macro, snapshot hash, rounding, transform, sidecar width, contact zone. Обновление hash при изменении не должно скрыть геометрическую ошибку: verifier не только сверяет целостность, но и повторяет расчёт. Include parser mutations with correct syntax but wrong semantics.

Особенно важны коварные случаи: оба конца свободны, середина collides; сопло свободно, duct collides; путь постоянного Z на поперечном склоне; материал появляется внутри текущего сегмента; уже напечатанный сосед ограничивает спуск; exit/parking unsafe; first cap над редким infill.

## Orca-specific integration

OFF/ZAA baselines; hybrid и ZAA mutual exclusion; mapping mm/scaled coords; отсутствие double E multiplier; no nominal-Z reset; order preservation; every export route; 3MF state and source reload; resolved preset/object override policy; filtered candidate changed after validation; GUI late result; app/config isolation; no post-processing execution.

## Независимые эталоны

Сравнение с тем же algorithm helper из planner не считается independent oracle. Минимально одна аналитическая проверка для каждого safety family; для малой сцены — другой медленный геометрический метод. ZAA и stock Orca используются для behavioral baseline, не для доказательства безопасности новой кривой.

## Протокол

В каждой записи: test ID, implementation commit, input/profile hashes, expected, observed, командa/exit code, platform, seed, elapsed time, stdout/stderr, artifact paths и residual assumptions. Run evidence сохраняется в форке, а не заменяет каталог запланированных сценариев.

Пропущенный обязательный тест блокирует release. Отсутствие условий для физического теста обозначается NOT_RUN и не скрывается успешной симуляцией.
