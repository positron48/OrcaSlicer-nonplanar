# Интеграция в OrcaSlicer

## Закреплённая основа

OrcaSlicer `v2.4.2`, commit `8500fcdccaa10b5099ac20d252af3a7c560046f1`. Доказательства — SOURCES O01–O03. Просмотр выбранных файлов через веб выполнен; сборка и полный call graph должны быть подтверждены агентом локально.

`upstream/source_map.json` перечисляет **существующие** файлы и маркеры. Предлагаемые новые классы и каталоги ниже не следует искать в stock как готовый API.

## Что переиспользовать

Импорт/размещение моделей, библиотеку профилей и их resolver, обычную нарезку тела, конфигурационную систему, 3MF, CMake/CTest/Catch2, GCodeWriter и нативный GUI. Существующий preview расширить, а не рисовать второй viewer на несогласованных координатах. STEP импортируется существующим OCCT-кодом; точность и units допроверяются (O07).

На вход нашего алгоритма передаются resolved-настройки и семантические траектории, а не только внешний G-code. Нельзя использовать комментарии ролей как единственное знание о форме дорожки. Штатные clearance-параметры Orca не подменяют полную геометрию головы.

## Что известно о ZAA

В `ContourZ.cpp` есть обработка выбранных ролей дорожек и высотные поправки относительно слоёв. `ExtrusionEntity.hpp` содержит трёхмерную полилинию и признак контурирования. Это полезная инфраструктура, но не контракт конечного положения сопла в нашем режиме (O04/O05).

В `GCode.cpp` у ZAA абсолютный Z образуется с добавлением nominal Z, а E получает специальную поправку. В этом же участке есть принудительные Z-переходы между контурами и обычными путями. Поэтому новый план хранит абсолютные XYZ и объём отдельно; прямое повторное использование ZAA-пути с большим смещением запрещено (O06).

Не менять upstream ZAA ради архитектуры новой крышки. Сравнение OFF/ZAA/HYBRID должно быть воспроизводимым на тех же исходных моделях. ZAA рассматривается как наблюдаемый baseline качества, а не независимый safety oracle.

## Карта вмешательства и риски

| Узел | Действие нового режима | Обязательная проверка |
|---|---|---|
| PrintConfig/GUI config | Namespaced ключи, выбор профиля, policy resolver | Нет обхода через inheritance/object override |
| Model/import/STEP | Исходная геометрия + доказуемая погрешность | Units, transforms, повторная тесселяция |
| Print/PrintObject steps | Cap partition до формирования окончательного тела | Top shell не восстанавливает вырезанный объём |
| Layer/Region/extrusion entities | Снимок планарных путей и support geometry | Реальная разреженная основа не становится сплошной |
| Новый планировщик | Transition/cap IR, порядок, переезды | Печатные движения не переставлены downstream |
| GCode/GCodeWriter | Адаптация явного объёма и абсолютных XYZ | Нет двойного flow/ZAA/nominal-Z преобразования |
| Cooling/прочие фильтры | Аудит, запрет неподдержанных преобразований | Финальные F/E/XYZ проверяются после фильтров |
| BackgroundSlicingProcess | Финальный candidate → verifier → gate | Не путать slice complete и verified |
| 3MF | Namespaced project state, без stale G-code | Round-trip, unknown schema, reload model |
| GCodeProcessor/GCodeViewer | Просмотр именно финального файла + sidecar roles | Replay по движению, не только по layer Z |
| CLI/export/upload | Общая policy и hash-bound gate | Ни один путь выдачи не пропускает проверку |

Конкретные функции подключения и threading нужно зафиксировать в Gate A. Большая часть PrintObject.cpp не является удобной точкой только потому, что там есть слово contour. Source-map — отправная точка аудита, не готовый патч.

## Предлагаемые новые модули

```text
src/libslic3r/Nonplanar/
  Types / Profile / Scene / Snapshot
  SurfaceAnalyzer / VolumePartition / PlanarAdapter
  TransitionSolver / PathPlanner / DepositionModel
  CollisionQuery / OrderAndTravelPlanner / MotionLimiter
  GCodeAdapter / VerificationProtocol / ExportPolicy
src/slic3r/GUI/Nonplanar/       # панели/связь с существующим viewer
src/nonplanar_verify/          # отдельный parser + replay executable
 tests/.../nonplanar/          # размещение согласовать с upstream tests
```

Это проектная структура, не обязательные имена файлов. Сохранять зависимости однонаправленными: геометрическое ядро не импортирует GUI; verifier не импортирует planner decision logic; GUI не вычисляет PASS самостоятельно.

## Стратегия интеграции тела

Первым исследовать нативную маску/объём cap-reservation до финальных perimeters/solid fill. Сгенерировать временную производную геометрию тела только внутри job snapshot; исходник на сцене и в 3MF не мутирует. Продемонстрировать, что тела с несколькими высотами и отверстием не получают потерю стены или дублированный top skin.

Точный выбор между изменёнными slicing surfaces и внутренним производным body mesh оформить ADR после spike. Оба варианта остаются внутри Orca и используют её planar engine. Выпиливание строк готового G-code не является допустимой заменой.

Первый ограниченный scheduler может печатать всё тело, затем доступные крышки; если высокое тело перекрыло низкую крышку, explicit fallback/reject. Чередование тела/крышек не обязательно в MVP и не должно возникать случайно из sorting по nominal layer.

## Stock behavior и обновления

Любой shared-патч тестировать относительно **немодифицированной сборки того же commit**. OFF: движения, E/F, материал и warnings совпадают после узкой нормализации метаданных. ZAA: сохраняется upstream алгоритм. Исключать из сравнения все Z/E/F или вырезать «неудобные» сегменты запрещено.

У экспериментальной сборки собственная идентичность приложения и config directory. Для обновления upstream создаётся отдельная ветка и выполняется повторный source audit, а не механический rebase с принятием всех новых golden-файлов.
